# Framework strings: answered questions

Questions about [rz-strings.md](../../rz-strings.md).

- **RZS2 — §§4–5, non-ASCII case conversion:** Determine the exact Windows runtime wide-case tables, owner-level handling of conversion failures and resulting search offsets when UTF-8 byte lengths change. Also determine non-ASCII registry strnicmp collation. [ASCII rules settled; raw conversion and malformed-input rules remain canonical in string-encoding.md and its prior MakeLower witness; no host Unicode folding substitution is specified.]

  **ANSWERED 2026-10-26 (re-rzs29):** MATCHES — §§4, 5.2 and 7.2 settle the C-locale table, exact shipped sub-0100 wide classification ranges, one-unit Windows mapping requests, identity on mapping failure, unconditional reassignment of the decoder's produced prefix, and unmodified lowered-byte search starts/results. Non-C registry ordering uses 256 independent byte-mapping replies, NUL-stopping prefix comparison and original-length ties. RZ66–RZ77 and DT27–DT30 are worked cases. The exact non-C case-pair replies for an installation cannot be read from the EXE: Windows NLS and the active CRT locale supply them. Section 5.2 states the remaining runtime observation precisely: capture OS/NLS version, actual locale handle/code page/support state, all 65,536 lower/upper unit results with eligible mapping counts, and all 256 registry byte-map replies plus locale flags/classification. This narrows that runtime-dependent remainder without substituting host Unicode folding or claiming a native run; string-encoding.md and its prior MakeLower witness remain canonical.

- **RZS1 — §7, callback reentrancy:** What is the supported result when a callback removes itself, removes another unknown callback, registers a replacement, or recursively invokes the same detokenizer? The observed service iterates its live ordered set and shares the per-token output between failed callbacks. Do not assume snapshot registration semantics. [Unknown; implement ordinary non-mutating callbacks first.]

  **ANSWERED 2026-10-26 (re-rzs29):** MATCHES — §7.1 specifies live node traversal, same-pass insertion above the current function address, removal of other nodes, unique-insert context retention, and no restart of value/named lookup. Self-removal followed by true is accepted; self-removal followed by false dereferences a freed iterator and has no supported deterministic result. Recursive calls run immediately with separate parser temporaries and shared registries/HTML mode, with no cycle/depth guard. DT20–DT26 are worked cases. Static instruction deductions only; no native execution or snapshot-registration semantics are claimed.

- **RZS8 — §§2/5, nonvirtual helper ABI for same-process shadows:** Please specify exact native prototypes and x86 calling conventions for Mid/Left/Right and MakeLower/MakeUpper, including substring return storage (hidden result pointer, ownership, construction/destruction obligations) and whether the case helpers return the receiver or no value. The spec gives behavior and entry addresses, but the SDK's cRZBaseString explicitly implements its own different class and does not establish these native signatures. [Do not guess signatures: monthly strings_shadow measures published virtual string operations and integer/string Sprintf; these nonvirtual helper paths remain excluded pending a native ABI contract.]

  **ANSWERED 2026-10-24 (re-rzstrings-rzs8):** MATCHES — §2.1 specifies the full x86 thiscall machine signatures: ECX receiver; hidden result-storage pointer first, then unsigned start/count for Mid or unsigned count for Left/Right; EAX returns the result pointer; callee removes 12 or 8 bytes respectively. Results are constructed in initially unconstructed 0x14-byte native storage, own their allocation, and require one direct non-deleting destruction. Case helpers take no stack arguments and expose no return value. RZ51–RZ54 cover result/lifetime and case boundaries. These are static instruction deductions, not a new native shadow run.

- **RZS11 — §4, empty-haystack Find exception:** For two independently constructed empty native strings, `Find("",0,true)` and `Find("",0,false)` both return 0xFFFFFFFF; core returns zero following §4's stated empty-needle rule (`start <= length`). Is the empty haystack an early failure exception? RFind on the empty witness agrees with core. [Keep empty-haystack Find excluded pending reconciliation; nonempty Find and empty/nonempty RFind remain measured.]

  **ANSWERED 2026-10-24 (re-rzstrings-rzs8):** DIFFERS — §4 corrects the previous rule: empty-needle Find succeeds only when start is strictly less than the counted length. The forward owner maps any result at the counted end to failure, so start equal to a nonempty haystack's length also fails. RFind retains min(start,length). RZ13 is corrected; RZ62–RZ65 cover both overloads, both sensitivities, end positions and reverse contrast. Static instruction evidence confirms the reported empty witness and extends it to the end-position case.

- **RZS6 — §5, Sprintf numeric conversion and unvectored flag combinations:** What exact digit conversion, default precision, rounding, exponent spelling, non-finite spelling and alternate-form rules apply to e/E/f/g/G, and what byte spelling does p produce? Please also pin integer zero with zero precision, alternate octal/hex prefixes and interaction of numeric precision with zero field padding. The syntax inventory alone does not define these outcomes. [Core owns parsing, argument selection, integer digits and field assembly; float/pointer digit conversion is an explicit caller-supplied FormatPrimitives boundary pending this answer, never an assumed whole-format host printf. Unvectored integer precision/prefix combinations use the literal conventional digit interpretation, marked in code; native parity for those combinations remains open.]

  **ANSWERED 2026-10-23 (re-rzstrings-rzs5):** DIFFERS — §5.1 and RZ21–RZ40 specify the bundled runtime's 17-significant-digit intermediate, decimal half-up rounding, default precision 6 (zero `g` precision means 1), precision cap 512, three-digit signed exponents, alternate floating forms and legacy non-finite text. Pointer output is eight uppercase hex digits without a prefix. Integer zero is never suppressed by zero precision; alternate octal/hex prefixes are unconditional, precision excludes prefixes and does not disable zero field padding, which precedes the prefix. Conventional host printf combinations therefore differ. The vectors are static RE deductions, not native execution measurements; RZS1–RZS5 remain separate.

  **ANSWERED 2026-10-27 (re-x-fw):** MATCHES — rz-strings.md section 5 now specifies both native splits: the first argument is one separator byte, the second the destination string, which is replaced.
